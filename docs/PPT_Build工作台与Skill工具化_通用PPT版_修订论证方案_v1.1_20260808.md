# PPT Build 工作台与 Skill 工具化修订论证方案

版本：v1.1  
日期：2026-08-08  
适用范围：面向广大用户的通用 PPT 设计与生产，包括商务汇报、课程培训、方案提案、数据报告、品牌发布、教育内容、社交媒体和视频视觉素材等场景。

## 一、结论先行

我们不应该把 `ppt-design-skill` 改造成一个固定模板生成器，也不应该只增加一个 Markdown 文件来提醒 LLM。

最合理的方案是建立三层结构：

```text
设计知识层：ppt-design-skill + ui-ux-pro-max
        ↓
动态设计层：LLM 根据当前内容临时编写 build.py
        ↓
执行控制层：Build 工作台负责运行、渲染、检查、版本管理
```

核心判断是：

> `ppt-design-skill` 负责“应该怎样设计”；Build 工作台负责“怎样稳定地把动态设计执行出来”。

这样既保留 Build 模式的灵活性，也能减少遗漏 skill、脚本执行错误、图片变形、字体过小、场景安全区被占用和版本混乱等问题。

## 二、问题背景与原因分析

### 2.1 imagegen 与 PPT skill 的差异

当前环境中的图像生成能力和 PPT 设计能力，确实存在不同的加载和执行机制：

| 项目 | imagegen | ppt-design-skill |
|---|---|---|
| Skill 层级 | 系统级 skill | Agent/项目级 skill |
| 工具关系 | 直接绑定图像生成工具 | 需要读取文档并动态编写脚本 |
| 产出方式 | 一次调用即可得到图像资源 | 多阶段编写、执行、渲染和检查 |
| 反馈方式 | 自动返回并显示生成图像 | 仅运行成功不代表视觉质量通过 |
| 主要风险 | 文字、构图、人物一致性 | 布局、字体、裁切、流程和 QA 遗漏 |

因此，问题不是简单的“skill 存储目录不同”，而是：

1. skill 的系统层级不同；
2. 是否绑定了直接可调用的工具不同；
3. 任务是否有自动反馈和自动检查不同；
4. PPT Build 模式本身需要动态编程，不能只依赖固定函数。

### 2.2 之前 PPT 产出不稳定的根本原因

此前的主要问题不是缺少 `build_helpers`，而是没有形成完整闭环：

- 没有始终把完整 skill 文档和参考文档作为当前任务的硬性上下文；
- 有时使用了 helper，但没有根据整套视觉系统组织页面；
- 生成成功被误认为设计完成；
- 没有稳定的渲染与逐页视觉检查机制；
- 版本、原型、完整 PPT 和修订脚本之间缺少统一的会话目录；
- 设计判断、脚本执行和 QA 检查混在一次临时操作中。

这说明我们需要增加执行层，而不是简单增加更多设计规则。

## 三、目标与非目标

### 3.1 目标

- 保留每一页由 LLM 动态编写 `build.py` 的能力；
- 自动加载 `ppt-design-skill`、`ui-ux-pro-max` 和 Build Helpers 上下文；
- 先制作两页原型，再决定是否扩展完整 PPT；
- 自动运行脚本、保存结果和建立版本记录；
- 自动检查元素越界、图片比例、文字尺寸、对比度和目标场景安全区；
- 明确区分“结构检查通过”和“视觉渲染检查通过”；
- 让每一轮修改都可以追溯、复现和回退。

### 3.2 非目标

- 不把 Build 模式改成固定模板；
- 不让所有页面套用同一种版式；
- 不用自动化替代视觉创意和人工审美判断；
- 不在没有渲染预览时声称视觉质量已经通过；
- 不直接修改系统级 skill 的原始文件，避免被更新覆盖；
- 不默默改变用户已经确认的内容、页序或视觉方向。

## 四、三层架构设计

### 4.1 设计知识层

由现有 skill 提供设计和实现知识：

- `ppt-design-skill`：PPT 模式、内容结构、Build Helpers、版式规则、字体、颜色和 QA 要求；
- `ui-ux-pro-max`：设计系统、字体组合、色彩、间距、信息层级、可读性和反模式；
- 项目素材：脚本、图片、角色素材、历史版本和已确认的品牌风格。

这一层解决“设计应该往哪里走”，但不负责直接完成整个项目。

### 4.2 动态设计层

由 LLM 根据当前任务临时生成 `build.py`。

这一层必须保留动态性，因为不同类型 PPT 的页面目标和信息关系不同。例如：

- 商务汇报可能使用数据重点页和结论页；
- 课程培训可能使用知识拆解页和练习页；
- 方案提案可能使用问题、策略和价值链页面；
- 数据报告可能使用图表、对比和趋势页面；
- 社交媒体或视频素材可能使用人物画面、巨大标题和互动引导页。

因此，页面坐标、元素数量、图片位置和 helper 组合不能全部预先固定。

### 4.3 执行控制层

由 Build 工作台负责：

- 创建会话目录；
- 准备 Python 运行环境；
- 提供 skill 文档和 API 上下文；
- 执行临时生成的 `build.py`；
- 调用渲染器生成页面预览；
- 执行结构和视觉 QA；
- 保存日志、预览图、报告和版本文件。

这一层是把 skill 从“说明书”提升为“可稳定执行的生产系统”的关键。

## 五、Build 工作台的推荐目录

建议在当前项目中建立项目级工作台，而不是直接改写系统 skill：

```text
项目根目录\ppt_workbench\
├─ pptwb.py                    # 统一入口
├─ config.json                 # skill、Python、渲染器和输出配置
├─ adapters\
│  ├─ skill_loader.py          # 加载 skill 和参考文档
│  ├─ uiux_adapter.py          # 调用 ui-ux-pro-max 搜索设计系统
│  ├─ build_runner.py          # 执行动态 build.py
│  └─ renderer.py              # PPT 渲染与截图
├─ checks\
│  ├─ geometry_check.py        # 越界、尺寸和层级检查
│  ├─ typography_check.py      # 字体、字号、行距检查
│  ├─ contrast_check.py        # 文字与背景对比度检查
│  ├─ image_check.py           # 图片比例、裁切和缺失检查
│  └─ narrative_check.py       # 页面角色和版式重复检查
├─ templates\
│  ├─ build_base.py            # 基础运行模板，不限定页面构图
│  └─ qa_rules.json            # 项目级检查规则
└─ sessions\                   # 每次任务独立保存
   └─ EP02_20260808_v0.1\
      ├─ brief.md
      ├─ content.json
      ├─ design-system.md
      ├─ design-tokens.json
      ├─ build.py
      ├─ output.pptx
      ├─ previews\
      ├─ qa-report.json
      └─ revision-log.md
```

## 六、工作台的完整工作流程

### 阶段 1：创建任务会话

输入：主题、受众、比例、页数、素材目录、使用场景、展示设备或发布平台。  
输出：独立会话目录、任务 brief、版本号和输出路径。

这一阶段解决“文件散落”和“版本混用”问题。

### 阶段 2：生成设计上下文

工作台自动准备：

- PPT skill 的完整规则；
- Build Helpers API；
- UI/UX 设计系统搜索结果；
- 项目字体和颜色 Token；
- 图片素材清单；
- 当前内容脚本和历史视觉记录。

输出：`design-system.md`、`design-tokens.json` 和页面级设计约束。

### 阶段 3：生成两页视觉原型

根据当前内容生成 2 页原型，必要时生成 3 套方向。

每套方向都必须满足：

- 视觉语法不同，而不是只换颜色；
- 页面构图不同；
- 图片使用方式不同；
- 标题层级清晰；
- 目标场景安全区保留，例如字幕区、移动端裁切区或投影边缘区；
- 文字在缩略图下仍然可读。

输出：多个独立的 `build.py` 和对应 PPT 预览。

### 阶段 4：动态编写并执行 Build 脚本

LLM 仍然临时编写当前任务专用的 `build.py`，工作台负责：

1. 检查脚本依赖和输入素材；
2. 使用固定 Python 运行时执行；
3. 捕获错误、警告和输出路径；
4. 保存脚本和日志；
5. 生成 PPT 文件。

工作台不替 LLM 决定每页如何设计，只保证设计脚本能够稳定执行。

### 阶段 5：渲染和 QA

检查分为两层。

#### 结构 QA

- PPT 能否正常打开；
- 页面比例是否正确；
- 元素是否越界；
- 图片是否缺失；
- 图片是否被拉伸；
- 字体和字号是否存在；
- 页数和文件大小是否合理。

#### 视觉 QA

- 标题是否足够大；
- 文字与背景对比度是否足够；
- 人物脸部是否被裁切；
- 文字是否压在复杂图片上；
- 是否满足目标场景的安全区和可读性要求；
- 相邻页面是否使用重复版式；
- 页面是否符合目标场景的阅读、讲解或观看节奏；
- 是否出现低级装饰、伪数据组件或无意义标签。

如果没有渲染器，报告必须明确写出“视觉 QA 未执行”，不能把结构检查结果当作视觉完成。

### 阶段 6：修订与重新生成

每次修订只针对明确问题，例如：

- 标题太小；
- 角色被裁切；
- 目标场景安全区不足；
- 页面节奏重复；
- 图片与文字争夺注意力；
- 视觉风格偏离已确认方向。

每轮修订保留：

- 原始脚本；
- 修订脚本；
- QA 报告；
- 预览图；
- 变更说明。

### 阶段 7：交付

只有满足以下条件才标记为可交付：

- Build 脚本已保存；
- PPT 能正常打开；
- 结构 QA 通过；
- 已完成渲染或明确记录渲染器缺失；
- 关键页面已人工确认；
- 输出文件采用统一版本命名。

## 七、建议的统一命令接口

以下是建议的工作台接口，不代表当前已经存在：

```text
pptwb init
pptwb design-system
pptwb prototype --pages 2 --styles 3
pptwb build
pptwb render
pptwb qa
pptwb package
```

一次完整任务可以简化为：

```text
pptwb prototype --topic "你不是太懂事" --pages 2 --styles 3
```

工作台生成三套两页原型后，由用户选择方向，再执行：

```text
pptwb build --style selected-A
pptwb render
pptwb qa
```

## 八、与单独说明文件、修改 skill 的区别

### 8.1 只建立 Markdown 文件

优点：简单、不会破坏现有环境。  
缺点：只是软约束，LLM 可能不读取、漏读或执行不完整。

它更像一份工作手册，不是工具。

### 8.2 修改 `SKILL.md`

优点：可以补充规则、规范和默认工作流程。  
缺点：依然主要依赖模型理解和执行，不能保证脚本一定运行、一定渲染、一定通过 QA。

它更像一本更完整的设计规范。

### 8.3 建立 Build 工作台

优点：可以自动执行脚本、生成预览、做检查和版本管理。  
缺点：需要编写运行器、渲染适配器和 QA 脚本。

它才是真正的执行层。

### 8.4 封装成插件或 MCP 工具

优点：可以被模型以明确工具调用方式使用，部分流程可以变成硬门槛。  
缺点：开发和维护成本更高，需要固定接口和运行环境。

这是最终的工具级形态。

## 九、分阶段落地建议

### 第一阶段：本地 MVP

只实现：

- 会话目录创建；
- skill 文档加载；
- Build 脚本运行；
- PPT 结构检查；
- 版本化输出。

目标是先解决“脚本、输出和版本不稳定”。

### 第二阶段：两页原型工作流

增加：

- UI/UX 设计系统调用；
- 3 套视觉方向生成；
- 2 页原型输出；
- 预览图和人工选择节点；
- 页面版式重复检查。

目标是解决“风格相似、缺少创意和没有先确认方向”。

### 第三阶段：完整 PPT 生产

增加：

- 整套 PPT 的页面角色规划；
- 按使用场景配置安全区规则；
- 图片素材自动清单；
- 渲染与逐页 QA；
- 修订日志和版本对比。

目标是稳定生成完整、可编辑、可复用的 PPT 与配套视觉素材。

### 第四阶段：插件化

把本地工作台封装为可调用工具，形成：

- `create_ppt_session`；
- `generate_prototypes`；
- `run_build`；
- `render_slides`；
- `qa_ppt`；
- `package_delivery`。

目标是让模型通过工具调用自动完成固定流程，而不是依赖临时记忆。

## 十、预期效果与边界

### 预期改善

- 每次任务都有独立会话和版本；
- 每份 PPT 都能找到对应的 `build.py`；
- 设计 skill 的规则不容易被遗漏；
- 结构错误能在交付前被发现；
- 视觉 QA 状态透明；
- 两页原型成为正式生产前的固定环节；
- 页面结构更容易实现真正的差异化。

### 不能保证的事情

- 工作台不能自动保证创意一定优秀；
- UI/UX 搜索结果不能代替内容判断；
- 自动检查不能完全代替人工审美；
- 如果没有可靠渲染器，就不能完成完整的视觉 QA；
- 中文字体在不同电脑上可能存在替换，需要建立字体检测和字体白名单。

## 十一、验收标准

Build 工作台达到可用状态，至少应满足：

- 一条命令可以创建独立 PPT 会话；
- 能自动读取项目内容和素材；
- 能调用 UI/UX 设计系统生成设计参考；
- 能保存并执行临时 `build.py`；
- 能生成两页原型和多套风格版本；
- 能报告元素越界和图片比例问题；
- 能明确报告渲染是否完成；
- 能自动生成版本化输出和 QA 报告；
- 不通过 QA 的文件不能被标记为最终交付。

## 十二、最终建议

建议采用以下路径：

1. 不直接修改系统级 `imagegen` 或 PPT skill；
2. 在当前项目中建立项目级 Build 工作台 MVP；
3. 保留 LLM 动态编写 `build.py` 的自由度；
4. 把运行、渲染、QA 和版本管理做成强制流程；
5. MVP 稳定后，再考虑封装成插件或 MCP 工具；
6. 不把工作台做成固定模板库，而是做成“动态 PPT 编程的执行和检查平台”。

最终目标不是让 PPT 生成变成机械的一键模板，而是让每次临时设计都具备稳定、可复现、可检查和可追溯的生产条件。
